The ECS Generation Pipeline, explained end-to-end

How a pile of annotated / historical CRFs becomes an Edit Check Specification — the list of data-validation rules for a study's Case Report Forms — walked through gradually, without asking you to read the code.

How to read this doc
Read it top to bottom — each section builds on the one before it, and you never need to open the code to follow along. We'll keep coming back to one running example: a study's Visit Date and Adverse Events forms. Watch those two travel through every step.

Two small reading aids:

  • Names in orange monospace are the exact function in the code, in case you want to go find it later. You can ignore them and still follow the story.
  • Little coloured tags tell you what kind of thing is being talked about:
INPUT/DOC a document or file STORE a database / index LLM an AI model call CODE a source file

The 60-second version

Think of a clinical study as a stack of forms that a hospital site fills in for each patient: Demographics, Adverse Events, Vital Signs, and so on. Every form has fields (boxes to type into), like "Visit Date" or "AE End Date".

Someone has to write the rules that catch bad data in those boxes — for example, "a visit date can't be in the future", or "if you pick Other, you must fill in the specify box". That list of rules is called the Edit Check Specification (ECS). Writing it by hand is slow and repetitive.

This tool does most of that work automatically. It lives inside Dataiku (a data-science platform), in a project called ECSGENERATION. You give it a study's CRF forms; it gives you back a table of rules, ready for a human to review.

Scope of this document
This walkthrough covers the one path that actually runs in production: a user uploads CRF forms, they are digitized, and each form is matched against the edit-check library (reusing rules where possible and generating the rest with an LLM). The Protocol-digitizer and the older vector-search matcher are not part of this path and are intentionally left out.

It works in two big moves:

Phase 1 — once per upload
Digitize the CRF
Read the uploaded PDF and turn it into a tidy list: which forms exist, which fields each has, and each field's ID code.
→
Phase 2 — per form
Match & Generate
For each form, look up rules we've used before in a shared library, reuse the ones that fit, and only ask an AI to write rules for whatever's left over.

The two phases are joined by one library of previously-approved rules (a search index called ecs_opensearch). Phase 2 reads from it.

The one thing to remember
The output is a table of rules for a human to review. Most of those rules are reused from the library, not invented — the AI only fills the gaps. So the tool is more "smart librarian" than "creative writer".

Wait — why "digitize" a PDF that's already on a computer?
Because a PDF is just pixels and text to a computer, not structured data. It can't answer "which forms are in here, and what fields do they have?" by looking at a PDF any more than you could answer it from a photo. Digitizing = reading the PDF and rewriting it as neat rows the next step can actually search.

The moving parts (the cast)

Only a handful of things do all the work. Here's the whole cast in plain terms — you can skim this and refer back later.

Places that store things

  • The library — an OpenSearch search index (ecs_opensearch) holding every rule we've approved before. Each rule is tagged Standard (applies to any study) or Historical (came from a specific past study). This is what Phase 2 shops in.
  • The notebook — a couple of Snowflake tables that just track progress ("this file is 40% digitized") and cost ("this run used N tokens"). Bookkeeping, nothing clever.
  • The inbox — folders where uploaded files land (file_upload for CRFs).

Tools that do the work

  • The AI — the ECS generation agent. Only used at the end, to write rules for fields the library didn't cover. (In the code: MyLLM.process() in ecs_generation_agent.py.)
  • PDF readers (pdfplumber, PyMuPDF) — read the text and the geometry of the CRF PDF. The geometry matters: it's how the tool tells the "field number" column from the "field OID" column by their position on the page.
  • rapidfuzz — a fuzzy text matcher. Lets "Conmeds" still find "Concomitant Medications" even though they're spelled differently.
  • LibreOffice — if you upload a Word .docx, it quietly converts it to PDF first (everything downstream expects a PDF).

One security note: the AI is reached through Dataiku's "LLM Mesh", so no API keys are hard-coded — credentials come from a stored secret (connection.get_dataiku_host_and_api_key(...)).

Phase 1 · Digitize the CRF — read the PDF, write neat rows

Goal of this phase: take the CRF PDF you uploaded and produce a simple list — for every form, its fields, and each field's OID. Nothing is matched or generated yet; we're just turning a PDF into data.

First, how the file gets in
When you upload a file, the tool saves it to a folder and writes a "0% done" row in a progress table so the UI can show a progress bar. If you uploaded a Word doc, it's converted to PDF first. Each upload gets an id (crf_file_id) that follows it through the rest of the pipeline.
In the code: file_upload() in ecs_utils.py → folder file_upload, table ecs_file_upload.

How the digitizer reads a form

The digitizer walks through the PDF page by page. Its whole job is to answer, for each form: what are its fields, and what OID does each field have? Here's how it does that in three steps.

In the code: extract_crf_new() → the HistoricalCRF class in crf_extraction.py.

Read the pages (and nudge the progress bar)

It opens the PDF and goes page by page. Every so often it updates the "% done" in the progress table so you see movement in the UI. That's all this step does.

Notice that there are two kinds of page

An annotated CRF prints two views of each form, and the digitizer treats them differently. It tells them apart by a simple tell: a page with the words "field name" on it is an OID page; everything else is a data page.

  • Data page — shows the human field labels and a small number next to each. From here it grabs the field name and its field number.
  • OID page — a lookup table that lists each field number next to its OID code. From here it grabs the field number → OID pairing. (It uses each word's position on the page to know which column is which.)
Both pages above are the Visit Date form from our example CRF. Notice the field number is the thing they share: the data page says field 3 is labelled "Visit Date", and the OID page says field 3 is VISDAT. That shared number is the glue for the next step.

Stitch the two views together

Now it joins them by field number: field 3's label ("Visit Date") + field 3's code (VISDAT) → one complete record. Do that for every field, drop exact duplicates, and Phase 1 is done.

For our example the Visit Date form comes out as:

{ "form_name": "Visit Date", "field_name": "Visit Date", "field_oid": "VISDAT" }
In the code: merge_sections_per_file(), then a join on field_number, then de-dup on (form_name, field_name).
Heads-up: three digitizer files look alike
The repo has three similar files (crf_extraction.py, thread_digitization.py, digitization.py). Only crf_extraction.py is the live one used here. If you go editing, make sure it's that one.

What Phase 1 hands to Phase 2

The end product is just a plain list of little records, one per field. This is the "data" version of your PDF — here are the real records for the Visit Date form from the 384-201-00002 run:

[
  { "form_name": "Visit Date", "field_name": "Was visit performed?",         "field_oid": "VISPERF"    },
  { "form_name": "Visit Date", "field_name": "If No, please provide reason", "field_oid": "VISREASND"  },
  { "form_name": "Visit Date", "field_name": "Visit Date",                   "field_oid": "VISDAT"     },
  { "form_name": "Visit Date", "field_name": "Folder OID (auto-populated)",  "field_oid": "FOLDER_OID" },
  ...
]

That's the whole output of Phase 1. Every field now has a stable OID code next to it — and as we'll see next, those codes (like VISDAT) are exactly what Phase 2 uses to find matching rules.

Where this list is parked between phases
The extract-crf endpoint (extract_crf()) is what runs the digitizer. It groups the records by form (skipping any field with no OID), saves the whole thing as JSON into the Snowflake ctl_crf_output table keyed by crf_file_id, and flips the progress row to 100%. Phase 2 later reads that same row back out — so Snowflake, not memory, is the hand-off between the two phases.
The real numbers for this run
Digitizing 384-201-00002_Annotated Unique CRF produced 76 forms and 915 field records, 831 of which carried an OID code. The handful without one are section labels / page noise (e.g. a stray "025 GMK (432)") — Phase 2 simply skips any form that has no OIDs.

Phase 2 · Match & Generate — turn that list into a table of rules

Phase 2 takes the list from Phase 1 and handles it one form at a time. For each form it does the same three things, in order:

step 1
Find similar forms
Look in the library for forms with a similar name.
→
step 2
Reuse rules that fit
Keep the library rules whose fields this study actually has.
→
step 3
Fill the gaps with AI
Only for fields nothing covered, ask the AI to draft a rule.

Most forms get most of their rules from step 2 (reuse). Step 3 (AI) is the fallback, not the star. The code that runs steps 1–2 is CRFFuzzyMatcher in review_table.py; step 3 is the generation agent.

No "AI search" here — it's simpler than that
A common assumption is that matching uses AI/semantic search. It doesn't. Step 1 is plain fuzzy text matching on form names, and step 2 is a plain set comparison of OID codes. The AI only shows up in step 3, to write brand-new rules. Keep that in mind as you read the steps below.

How Phase 2 gets started

The front-end kicks off Phase 2 by calling the generate-review-table endpoint (review_table()). That function reads Phase 1's saved output for this file_id back out of Snowflake (the ctl_crf_output table), then runs steps 1–2 with CRFFuzzyMatcher (fit threshold 0.62) and returns the assembled rows.

Step 3 — the AI fill — is a separate endpoint. Only for the forms/fields nothing matched does the front-end call generate_ecs_llm(), which hands the work to a pre-built Dataiku agent and logs the token cost. So "start matching" and "call the AI" are two different calls; we'll unpack the agent in step 3.

Gotcha for future editors: the AI prompt is copy-pasted in 3 places
The exact same "Edit Check Specification Specialist" prompt lives in three files and they've drifted apart. The one that actually runs is in ecs_generation_agent.py. If you want to change how the AI writes rules, change that copy.

Step 1 — find library forms with a similar name

For each study form, the tool searches the library for forms whose name looks similar — using fuzzy text matching, not exact spelling. So the study's "Conmeds" form still finds the library's "Concomitant Medications".

This is a deliberately loose first pass. It's just narrowing down "which library forms are worth looking at" — the real decision happens in step 2.

In the code: get_standard_crf() using rapidfuzz, similarity cutoff 70.

Step 2 — reuse the rules whose fields this study has

Now the important bit. For each similar library form, the tool pulls its rules and asks one question per rule:

"Does this study have all the fields this rule needs?"
If yes → reuse the rule. If no → skip it.

It answers by comparing OID codes, not names. Every library rule lists the OIDs it needs. If those OIDs are all present in the study (a subset of the study's OIDs), the rule fits and is copied into the output.

Example. The library has a rule AE_002: "End Date can't be before Start Date." It needs the fields AEENDAT and AESTDAT. Our study's Adverse Events form (from Phase 1) has both of those OIDs → the rule fits → it's reused, word for word, tagged with the study's own form name.

The "fits / doesn't fit" call on real data

In the 384-201-00002 run, the study's Visit Date form fuzzy-matched the library's Visit Date rules — 13 Historical candidates. The tool then compared each rule's OIDs to the study's OIDs:

Library ruleOIDs it needsStudy has them all?Result
VISDAT_901['VISDAT','DSSTDAT_IC','DSSTDAT']No — the study has VISDAT but not all threeskipped
the other 12 (e.g. VISDAT_902)['VISDAT']Yesreused

So twelve Visit Date rules were reused verbatim and one was dropped — and in the final output the Visit Date form carries exactly those 12 Historical rules, with zero AI needed. That single-OID pattern (['VISDAT']) is why almost all of them fit.

The tool does this for two flavours of library rule:

  • Standard rules — generic, apply to any study (e.g. "this date field can't be blank").
  • Historical rules — from a specific past study, narrowed to ones tagged with this study's molecule (falling back to indication, then therapeutic area).
Why match on OID codes instead of field names?
Because names are unreliable — one study writes "AE End Date", another writes "End date of adverse event". The OID code AEENDAT is the same in both. Comparing codes lets the tool safely say "yes, this study really does have the field this rule needs", which sloppy name-matching could get wrong.
Where this lives in Dataiku
The matcher reads the index named by the ecs_opensearch project variable — ${projectKey}_ecs_index → ecsgeneration_ecs_index — browsable as the Dataiku dataset ecs_index (~4,800 rows, 17 columns). Each row is one rule, and it carries the columns that matter here: form_field_value, validation_logic, reasoning, action/action_details, validation_id, ecs_id, field_oids (an array, populated for ~100% of rows), source, and the study tags indication/molecule/ta. Filter on source to switch between Standard (study-agnostic boilerplate) and Historical/Historic (study-specific). The field_oids column is the one the is_subset() check reads.
Don't confuse it with ecs_index_data
There is a second, similarly-named dataset ecs_index_data (the standard_index = ${projectKey}_ecs_index_data). It holds only Standard rows, has no field_oids column (it carries form_name_vector/form_field_vector embeddings instead), and is not what the live matcher queries. Use ecs_index for anything OID-related.

What a library record looks like

Real rows from the ecs_index dataset. The tell is the study tags: Standard rows leave indication/molecule/ta empty (they apply to any study), while Historical rows carry them (they came from a specific past study):

sourceform_namefield_oidsindication / molecule / tavalidation_idthe rule

A puzzle this explains: "why is my IgA study full of depression rules?"
The library mixes rules from many past studies. Our example study uses molecule MSP-2020, and the only past study with that molecule happened to be a Treatment-Resistant Depression study. So when the tool keeps the MSP-2020 Historical rules, they carry that old study's tags (TRD / Neurology) — even though your new study is IgA Nephropathy. The rules still fit (they're matched by OID codes, which don't care about indication), the tags just reveal where they came from. That's why tool_output.csv shows depression tags on an IgA run — it's expected, not a bug.

Step 3 — ask the AI for whatever's left

Some fields won't match any library rule. For those — and only those — the tool asks the AI to write a rule. It sends the AI the form name and the leftover field names, with one firm instruction: don't make things up; if you're unsure, just say the field can't be blank.

The AI returns, for each field, a plain rule: what to check, why, and the message to show. If it skips a field or the call fails, the tool falls back to a safe default ("must not be blank"). These rules are tagged LLM Generated so a reviewer knows they weren't reused from the approved library and deserve a closer look.

In the code: make_llm_call_batch() → parse_llm_batch_output(), with create_default_validation() as the fallback. Temperature 0 (as deterministic as possible).

Phase 2 in one breath
For each form: find similar library forms → reuse every rule whose OID codes fit this study → ask the AI to write rules only for the fields nothing covered → collect it all into one review table.

Reference · The API endpoints & call order

Everything above is driven by six HTTP endpoints, split across two Dataiku API services (defined in api_designer/). The front-end calls them in a fixed order for one upload:

Upload the file

POST /file-upload/run → file_upload(user_id, file_b64, file_name)
Saves the file, converts docx→pdf, opens the progress row, and returns the crf_file_id everything else keys off.

Digitize it (Phase 1)

POST /extract-crf/run → extract_crf(file_path, file_id, created_by)
Runs the digitizer, writes the form/field/OID JSON to ctl_crf_output, sets progress to 100%.

Poll the progress bar

POST /digitization-percent/run → digitization_percent(file_id)
Reads digitization_percent + description from ecs_file_upload; returns e.g. {"response":"40%","message":"…"}. Called repeatedly by the UI while digitization runs.

Fill the study-filter dropdowns

POST /get-indication/run → get_indication()
Returns the distinct indication / molecule / therapeutic_area values present in the library index (minus "Not Found"/"nan"), so the user can pick which to match against.

Match & reuse (Phase 2, steps 1–2)

POST /generate-review-table/run → review_table(file_path, file_id, indication, molecule, ta)
Reads ctl_crf_output for the file, runs CRFFuzzyMatcher (threshold 0.62), returns the reused/placeholder rows.

Generate the leftovers (Phase 2, step 3)

POST /ecs-generation/run → generate_ecs_llm(form_name, fields, file_id, user_id)
Sends the unmatched form + fields to the generation agent and logs token usage. This is the only endpoint in the separate ecs-platform-agent service.

Reference · The review table (the output)

This is what you get back: one row per rule. A person then reviews it, keeps the good rows, and fixes the rest. Internally each row carries these fields:

[
  "original_form_name",  // what the study's form was called
  "original_field",      // the study's field name
  "source",              // "Standard" | "Historical" | "LLM Generated"
  "form_name",           // matched library form
  "form_field_value",    // matched library field
  "score",               // match confidence
  "form_domain_name",    // e.g. AE, DM, VS
  "variable_name",       // UPPER_SNAKE_CASE
  "validation_logic",    // the edit-check rule
  "reasoning",           // why the rule exists
  "action",              // what fires
  "action_details"       // the exact instruction / message
]

The most useful column for a reviewer is source. It's the honesty flag: Standard/Historical means "reused from the approved library, probably fine"; LLM Generated means "the AI wrote this, read it carefully".

What the exported CSV actually looks like

The internal shape above gets flattened into the delivered spreadsheet with these column headers: VALIDATION ID, INDICATION, MOLECULE, THERAPEUTIC AREA, DOMAIN NAME, FIELD OIDS, VARIABLE TEXT, SOURCE, VALIDATION LOGIC, REASONING, ACTION, ACTION DETAILS, ECS ID. SourceDomainField OIDsValidation logicReasoningAction details

In the 384-201-00002 output the split is 697 LLM Generated, 140 Standard, 73 Historical — 910 rows total.

Reference · Quirks worth knowing

Small surprises that will save you time if you ever dig into the code or the data.

  • Matching is by OID codes, not field names. If you remember one thing about Phase 2, remember this.
  • The "does it fit?" check pools OIDs across all forms, not per form. It compares a rule's OIDs against every OID in the whole study at once (variable fecthed_all_field_oids). A per-form version exists in the code but is commented out.
  • field_oids is stored as a string in the index and parsed back with ast.literal_eval before comparison.
  • The "source" tag is spelled inconsistently across files — the current matcher uses Standard/Historical. Check which spelling the target index actually uses before changing a filter.
  • Three CRF digitizers coexist in the repo (crf_extraction.py, thread_digitization.py, digitization.py); only extract_crf_new in crf_extraction.py is the live OID-aware path used here.
  • Token usage is logged from api.py into the table named by the llm_token_usage project var, keyed by crf_file_id under workflow "ECS Generation Agent".
  • The generation prompt is duplicated three times. The live copy is inside the agent (ecs_generation_agent.py → MyLLM.process); near-identical copies live in utilities/llm.py and in CRFFuzzyMatcher (review_table.py). They have drifted — change the agent copy for the api.py path, and beware the others going stale.
  • Two API entry points, two ids. ecs_utils.py file_upload mints a uuid it calls protocol_id internally but stores as crf_file_id; api.py then uses that same id as file_id/user_id in places. Trace the id carefully — the naming isn't consistent across files.
