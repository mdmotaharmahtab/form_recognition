The unknown-format CRF digitizer, explained end to end

Given any CRF PDF — annotated or not, any vendor, any layout, up to 1000 pages — the pipeline extracts every data-entry field as (form_name, field_name, page). It does this with a handful of LLM calls per document (the Rave book took 7; hard cap ≈16, regardless of page count), because the LLM never reads the document. It writes a small parser for it, and plain Python runs that parser over every page.

■ deterministic Python — runs on all pages, costs nothing ■ LLM call — Claude Sonnet 4.5 via Dataiku LLM Mesh ■ feedback loop — bounded, self-stopping

Every example below is taken verbatim from a real run on a 404-page Medidata Rave CRF (study 384-201-00002). Two other formats — a 609-page eSource layout and a 913-page form tracker — went through the identical pipeline with zero code changes.

1The problem: parse a format you have never seen

In one sentence: CRFs arrive in endless visual formats, and the only thing we know in advance is “this is a CRF”.

Our production digitizer understands one format: annotated Medidata Rave, where every field prints its machine ID (OID) in brackets next to it. Real studies send everything else — eSource exports, form trackers, scanned questionnaires, vendor-specific books. Three real examples from the test set:

Real pages, rendered from the PDFs. Left: Rave prints one field per ruled row with a numbered circle at the right edge. Middle: the eSource book prints numbered activities on a blue boilerplate template with date/initials placeholders. Right: the form tracker is a landscape table, one field per row. Three unrelated visual languages — and the pipeline may not assume any of them, because book #4 will look different again.

Two obvious approaches, and why both die

✕ Write a template per format

Somebody has to notice each new format, study it, and hand-code a parser. The format space is unbounded — the three books above already use three unrelated layouts. This is a permanent engineering backlog, not a pipeline.

✕ Let an LLM read every page

The test books are 404–913 pages. Per-page LLM extraction means ~900 calls per document, minutes of latency, real money, and a different answer every run — with no way to audit why a field appeared. Non-deterministic extraction can’t back a regulated pipeline.

The insight the whole pipeline is built on: inside one document, layouts repeat massively. A 404-page CRF book is not 404 novel pages — it’s a handful of page skeletons (5 for this book), stamped over and over with different words. So: show an LLM one example of each skeleton (6 pages here), have it write code that parses those skeletons, then let cheap deterministic Python run that code over all 404 pages. The LLM is used as a programmer, not a reader.

In one sentence: each PDF page is reduced to a list of Line objects — the text plus where it sits and how it’s styled — which is cheap, exact, and language-agnostic.

Born-digital PDFs carry a text layer, so no OCR and no vision model is needed. PyMuPDF gives us every text span with coordinates; we merge spans into lines and keep five things per line: text, x/y position, font size, boldness, color. 3Layout clustering: 404 pages → 6 pages worth reading

In one sentence: every line becomes a small typography token that ignores the words; a page is its set of tokens; the document’s own boilerplate is discovered and discounted; pages stack by similarity — with the one threshold picked by the document itself.

→

Clustering has one job: sort pages into piles that print the same way — like sorting mail by envelope shape without reading the letters. Everything that changes between two pages of the same layout (the words) is ignored; everything that stays constant (position, size, styling, the kind of text) is kept. Five steps, all pure Python, no AI involved.

Step A — turn every line into a typography token

A token is a 5-part description of how one line is printed: (x-band, size, bold, color, character-class). For example (5, =, ·, ·, num) reads: starts in the right-most sixth of the page, normal font size, not bold, black ink, digits only — that is a field-number column, and the description stays true whatever the numbers are. That is the entire vocabulary: 6 × 3 × 2 × 2 × 5 = 360 possible tokens, of which a real book prints only a few dozen distinct ones (the QSC book: 25 across 609 pages).

So the 25 lines of page 133 collapse into just 6 distinct tokens — one per visual role in the page-133 table — and that set of six is the page’s entire profile. Two details make the profile stable across pages of the same template. It records which token kinds exist, not how many: a form asking 3 questions and one asking 5 produce the same set (count_transform_sweep.py measured set-membership beating counts on every book). And it skips vertical position: y tells you how full a page is, not which template printed it.

Why ignoring the words is the whole trick: page 133 is “PK Plasma Samples: 24 Hours”. The other 149 pages of its stack — Fluid Biomarkers, Drug Screen Test, Central Laboratory… — ask completely different questions, but print them with the same skeleton: labels starting in band 0, answer options in band 4, a number column in band 5. Same token set → same stack, all 150 of them. Teach the parser one of these pages and you have parsed all 150.

Step B — discover the document’s own boilerplate (“chrome”)

Some tokens say nothing about which template printed a page — because the document prints them on every page: its own headers, footers, form frames. The pipeline discovers these per document and discounts them smoothly:

weight(token) = 1 − (pages containing it / all pages)³

A token on every page weighs 0; on half the pages ≈ 0.88; a rare one ≈ 1. “Chrome” is simply whatever this document repeats everywhere — its headers, footers, form frames — so the list is rediscovered from scratch for each document. A real example of why the discount matters: the QSC eSource book prints only 25 distinct tokens in total, and 11 of them appear on all 609 pages. Before damping, that chrome carried 85–94% of every page’s weight, so every pair of pages looked ≥50% alike and the whole book fused into one pile (diagnosed in qsc_merge_diag.py). After damping, similarity is computed on what remains — the tokens that actually distinguish templates:

Step C — stack pages by weighted similarity

Step A gave every page a profile (its set of tokens) and Step B gave every token a weight. Two pieces are still missing: a number that says how alike two pages are, and a procedure that turns those numbers into piles. Both are standard tools — here is each concept first, then what the pipeline does with it.

Concept 1 · Jaccard similarity — what fraction of the combined set is shared?

The classic way to compare two sets: divide what they share by everything either one has. The sets {▲ ● ■} and {● ■ ◆} share 2 of the 4 distinct symbols, so J = 2⁄4 = 0.5; identical sets score 1.0, sets with nothing in common 0.0. The weighted version lets each symbol count its Step-B weight instead of 1 — a shared token that lives on every page (chrome, weight ≈ 0) adds almost nothing to the score, so similarity is decided by the tokens that actually distinguish templates. Two real comparisons from the Rave book:

same stack — J = 1.000

Page 133 (“PK Plasma Samples: 24 Hours”) vs page 2 (“Visit Date”). Completely different questions — but both pages produce exactly the same 6 tokens from Step A. Shared weight 1.97 ÷ union weight 1.97 = 1.000 ≥ θ → same stack.

different stacks — J = 0.108

Page 133 vs page 214, a data-dictionary page (“PANSS” appendix). p214 prints 14 tokens — mid-page columns of code and num lines that p133 doesn’t have. They share 5 tokens, but mostly featherweight ones: shared weight 1.02 ÷ union weight 9.46 = 0.108 < θ → different stacks. (Unweighted Jaccard would say 0.33 — uncomfortably close to θ=0.35. The Step-B weights make the call decisive.)

Concept 2 · Leader clustering — one pass, piles grow around anchor pages

With the similarity defined, the piles are built in a single pass: take the next page, compare it to the founding page (“leader”) of every existing pile, and either join the best match — if that similarity clears the threshold θ — or found a new pile. Pages are processed densest-profile-first, because a dense page is the best anchor for its template (the order is computed from content, never from position in the PDF, so shuffling the document changes nothing — audit T4, Rand 1.000). The real pass over the Rave book — only 11 of 404 pages ever founded a pile; everyone else joined one:

p75 17 tokens founds pile 1 ← densest page in the book (a data-dictionary page) p311 16 tokens joins pile 1 J=0.65 p70 16 tokens joins pile 1 J=0.79 p98 16 tokens joins pile 1 J=0.91 … 210 more dictionary-family pages join pile 1 … p162 10 tokens founds pile 2 ← first entry-form page (“Barnes Akathisia Rating Scale”): … best existing match was J=0.27, below θ — new pile result of the pass: 11 piles, sizes 214 · 77 · 57 · 27 · 13 · 6 · 3 · 2 · 2 · 2 · 1

Concept 3 · Centroids — a pile’s average profile, used to clean up the greed

A one-pass algorithm over-splits: above, the entry-form family ended up scattered across four piles (77 + 57 + 13 + 3 pages), because each pile is anchored to one founding page, and a single page carries noise — one odd token can hold two halves of the same family apart. The fix is to compare piles by their centroid: the average of the members’ profiles, where a token on every member counts 1.0 and one on half the members 0.5. Averaging washes out per-page noise. Two cleanup passes run: (i) merge piles whose centroids clear θ, (ii) one sweep re-homing each page to its best-matching centroid (a page that joined early, while its pile was still forming, gets a second look). On the Rave book the merge snaps the fragments back together:

greedy piles: 214 + 27 + 6 + 2 77 + 57 + 13 + 3 2 2 1 └────────┬───────┘ └────────┬───────┘ centroid merge: 249 data-dictionary 150 entry forms 2 2 1 → 5 stacks

“Is this k-means?” Same family — centroid-based partitioning — and cleanup pass (ii) is literally one k-means assignment step, just with weighted Jaccard in place of Euclidean distance. Three things are deliberately different, each forced by a requirement:

k-meansthis step
cluster count k must be chosen up front emerges from the similarity bar θ — an unknown book may have 2 templates or 35 (this corpus has both), so no count can be preset. Step D picks θ, which is where k-means users reach for elbow/silhouette heuristics
procedure iterate assign → update from a random start until convergence; different seeds, different answers three fixed passes — greedy build, centroid merge, one reassignment sweep — fully deterministic: same PDF, same stacks, forever
data & distance points in a vector space, cluster mean weighted token sets and Jaccard — the k-means cousins for such data are k-medoids / k-modes

One assignment pass instead of looping to convergence is enough here because clustering only steers sampling (§3E): a slightly suboptimal pile costs a prompt slot, never a field.

Where this comes from: Jaccard-over-shingles is the textbook technique for “were these two documents produced from the same template?” — Broder’s near-duplicate detection that de-duplicated the early web. At web scale it is approximated with MinHash; at ≤1000 pages the pipeline just computes it exactly, keeping determinism and zero dependencies.

Step D — the document picks its own θ

Everything above used one number: θ, the similarity a page must reach to join a pile. Set it too high and one template splits into fragments; too low and different templates fuse. Any fixed value shipped in the code would be a guess tuned to somebody’s sample documents — so instead, the pipeline measures which θ the document itself is indifferent to. Two ideas make that work: first why a document can be indifferent to θ at all, then a way to test that indifference.

Concept · the similarity gap — why nudging θ usually changes nothing

Put the six real scores from Concepts 1–2 on a line. Pages of the same template score high (0.65–1.00); pages of different templates score low (0.11, 0.27). Between the two groups: a wide empty stretch where no score falls at all —

θ’s whole job is to fall between the two groups. For these pages, θ = 0.30 and θ = 0.60 make every decision identically — the piles are a fact about the similarities, and θ only has to land somewhere in the hole between them. That is the signal being hunted: like tuning a radio, the station holds steady across a stretch of the dial while static changes with every nudge — a real structure is exactly the thing that does not depend on the knob’s precise position.

At 404 pages the picture blurs: a few borderline pages land inside the gap, so the full book’s answer won’t stay identical across the entire stretch — where it stops holding has to be measured, not eyeballed. And “the same piles came out” needs a precise meaning when comparing two 404-page clusterings. That measuring stick is the second concept:

Concept · the Rand index — do two clusterings agree?

Take every pair of pages. Ask both clusterings the same yes/no question about each pair: “are these two pages in the same pile?” The Rand index is the fraction of pairs where the two answers match — 1.0 means the clusterings are the same partition in different clothes. A worked example with 4 pages, clustering X = {1,2}{3,4} vs clustering Y = {1,2,3}{4}:

The selection — sweep θ, find where the answer stops changing

The pipeline clusters the document at every θ on a fixed grid (0.30 to 0.60 in steps of 0.05), computes the Rand index between each pair of neighbouring partitions, and marks a pair stable when Rand ≥ 0.97 — statistically the same partition. The longest run of stable pairs is the document’s plateau: the part of the similarity gap that survives contact with all 404 pages. θ* is the middle of that plateau — the spot farthest from both cliffs (fragmenting above, fusing below). The reasoning is the radio dial again: structure that survives a range of thresholds belongs to the document; structure that appears at exactly one setting is an artifact of the knob. Two boundary rules: ties prefer the looser plateau (over-merging is the repairable miss — a hidden layout resurfaces as a zero-record stack on the §6 coverage map — while over-splitting silently burns representative slots), and the grid ends at 0.30/0.60 because below 0.30 “same layout” would mean sharing under a third of structural mass, while above 0.60 it would demand a near-identity that per-page content jitter never allows.

Step E — pick the representatives the LLM will read

Representatives are picked biggest-stack-first until 95% of pages are represented (at most 10 stack picks); a dominant stack (>50 pages) contributes two examples; pages 1–2 are always added on top because they carry the document’s identity (title, TOC) — so a heterogeneous book can reach 12 representatives. Stacks made entirely of blank pages never get a representative at all — an empty dump is a prompt slot the LLM can’t learn from, even when slots are left over. “Isn’t this just hardcoded to your sample books?” — the audit that says no. generalization_audit.py checks the properties hardcoding would break, on CRF books and foreign documents:
  • Word-blindness, proven: replace every word on every page with garbage of the same shape — profiles are bit-identical, the partition doesn’t move (Rand 1.000, all 7 documents).
  • No magic numbers: the damping exponent works identically from 2 through 5 (a plateau, not a knife-edge); grid endpoints are structural properties of Jaccard; θ itself is selected per document.
  • Chrome adapts: concatenate two different books into one “document” and cluster — every large stack stays 100% single-book. Chrome discovery keys on each document’s own repetition, not on anything learned from ours.
  • Order-invariant: feeding pages in reverse produces the identical partition (canonical processing order).
  • Tiny documents degrade gracefully: a 2-page “book” just sends both pages to the LLM.
  • Labels are tests, never inputs: the known page pairs (“3 and 10 are the same template”, “title ≠ form ≠ dictionary”) are used to check the selected θ — they never influence it.
History — the five-signal fingerprint v1 this replaced, and why

The first front-end hashed five hand-picked page statistics into a tuple — % bracket-only lines, % integer-only lines, % colored lines, a line-count band, and a 4-bin x-histogram — and stacked pages with exactly equal tuples. It worked (23 stacks / 88% repped on the Rave book) and even survived out-of-domain stress tests on protocols and contracts (8–24 stacks, 78–100% repped, ood_cluster_probe.py). But it had an honesty problem we ourselves documented: two of the five signals were corpus-scented — “bracket-only lines” encodes the Rave OID annotation convention, “integer-only lines” the numbered-form convention. Inert on documents without those conventions, but a reviewer who works with CRFs daily would rightly call them learned from our five sample books.

The generic profile above removes the objection at the root — no named convention anywhere — and then beat v1 on its own metric on every book:

LLM call #1 — the prompt
  • The contract: reply with one function def extract(pages); input is every page’s Line list; return {form_name, field_name, page} dicts.
  • The evidence: the 6 page dumps from §3, each tagged with its stack size (“this layout covers ~249 pages”) so the model knows what matters.
  • Hard rules: key on structure (position, boldness, size, patterns), never on specific question wording — the code must work on the 398 pages it hasn’t seen. Standard library only. No I/O.
  • Quality bar: labels must be human-readable; every record must carry the real 1-based page number.
The reply — ~120 lines of document-specific Python

Sonnet 4.5 studied the dumps and chose its own landmarks for this book — none of these rules exist anywhere in our codebase:

  • form name = bold line matching Form: … in the header band (y ≈ 100–120), carried across pages
  • pages containing Field Name Data Type are the data-dictionary appendix → skip
  • field labels live at x = 90–100, font size ≈10, between the header and footer bands; right-column answers (x > 350) are dropped
  • ~15 noise filters it invented: page numbers, answer options, machine-code prefixes, time-point lists, signature-page legal words (pursuant / certify / attest)

from collections import namedtuple

def extract(pages):
    results = []
    current_form = ""
    
    for page_idx, lines in pages:
        page_num = page_idx + 1
        
        # Check if this is a data dictionary page (has "Field Name Data Type" header)
        is_dict_page = any(
            line.text.strip() == "Field Name Data Type" 
            for line in lines
        )
        if is_dict_page:
            continue
        
        # Look for form name in bold "Form: <name>" pattern at y~104-118
        for line in lines:
            if line.bold and line.y0 >= 100 and line.y0 <= 120:
                match = re.match(r'Form:\s*(.+)', line.text.strip())
                if match:
                    current_form = match.group(1).strip()
                    break
        
        # Extract fields: left-aligned questions at x=90-100
        for i, line in enumerate(lines):
            text = line.text.strip()
            
            # Skip empty, headers, footers, page numbers
            if not text:
                continue
            if line.y0 < 140:  # Skip header area
                continue
            if line.y0 > 680:  # Skip footer area
                continue
            
            # Field questions are at x=90-100, size=10, not bold typically
            if line.x0 >= 90 and line.x0 <= 100 and line.size >= 9.5 and line.size <= 10.5:
                # Skip known non-field patterns
                if re.match(r'^\d+$', text):  # bare numbers
                    continue
                if re.match(r'^\d+\s+of\s+\d+$', text, re.IGNORECASE):  # page numbers
                    continue
                if text in ['Yes', 'No', 'If No', 'If Yes']:  # answer options
                    continue
                if re.match(r'^(Fixed Unit|Units|Values|Pre-Filled|Include|Field Name|Data Type|Field OID)', text):
                    continue
                
                # Skip answer option patterns at x~408-492
                if line.x0 > 350:
                    continue
                
                # Skip lines that are continuations (check if previous line at similar x was a field)
                # Multi-line questions: only take first line, or merge intelligently
                # For simplicity, if this line starts with lowercase or common continuation words, skip
                if i > 0:

                    if (abs(prev.y0 - line.y0) < 15 and abs(prev.x0 - line.x0) < 10 
                        and prev.x0 >= 90 and prev.x0 <= 100):

                        if text[0].islower() or text.startswith('assessed'):

                field_name = text

                # Keep the question mark if present

                    continue

                    continue

                answer_patterns = [

                    r'^(Absent|Minimal|Mild|Moderate|Severe|Extreme)$',

Note two of its choices — they become §7’s story. There is no filter for the checklist instruction “Check all that apply”, so it is extracted as a field; and its own answer-option pattern ^\w+\s+(Lead|Continuous|Recording) — written to drop right-column option text like “Holter Continuous Ecg Recording” — also matches real field labels that begin with “ECG Recording …”, silently deleting four fields on every Holter ECG page. Both mistakes pass every mechanical gate; both get caught by the page-grounded audit.

Why code instead of answers? An answer (“here are the fields on this page”) is consumed once and can’t be checked. A program is an inspectable artifact: we can run it on all 404 pages for free, measure exactly what it caught and where it’s blind, diff two versions of it, re-run it bit-identically next month, and read it line by line in a validation review. Determinism and auditability come for free.

Fresh Python subprocess per run (sandbox_runner.py). No shared interpreter state, killable from outside on timeout, memory-capped. The parent only ever parses a JSON result — never imports the generated module.

8The loop, the score, and when it stops

In one sentence: generate → run → gate → confirm → audit → score, at most 5 parser versions, stopping early on convergence or on two non-improving versions — and the best version is exported, never the last.

inper version: the gates verdict (§6) + audit issue count (§7) + page coverage — the raw material of the score tuple.
→
outa decision — continue (targeted revision prompt back to §7c) or stop (converged / plateau / budget / error) — plus the best version; every cycle logged in codegen_trail_claude_4_5_sonnet.json.

The score — one tuple, compared left to right

( blockers,  audit_issues,  warnings,  −pages_covered )

Lower is better. A version that fixes a blocker always beats one that adds coverage; audit issues outrank warnings; coverage breaks ties. A never-audited version scores its audit slot as infinity — it can be kept, but it can never look better than an audited one.

Guards that keep the comparison honest

  • re-audits reuse the same fixed page sample — no lucky re-rolls
  • a version that keeps less than 90% of the previously covered page set is never “an improvement”, however clean its audit — and it’s the set, not the count: covering the same number of pages while swapping which pages still counts as losing them
  • the best-scoring version is exported, not the most recent one — a bad v4 can’t destroy a good v2
converged — gates pass, audit finds 0 issues, and it’s the new best plateau — two consecutive versions fail to beat their predecessor: diminishing returns over two runs, stop. One stall is tolerated — audit counts come from a small page sample, so a single noisy count must not end a document. (Exception: two crashed versions in a row aren’t “diminishing” returns, they’re zero — the loop keeps revising until the cap) budget — hard cap of 5 versions (≈ 16 LLM calls worst case, audit reprompts included) error — transport/audit failure: stop loudly, keep what’s banked

Name → OID mapping (the downstream join)

This is a different question from the 87% / 66% above. Those numbers measured how well the parser read the pages. This step takes the names it read and looks each one up in the ecs_index library of known forms/fields/OIDs — unannotated CRFs print no OIDs, so a library lookup by name is the only way to get one. One framing fact first: production has no such step to reuse. Annotated Rave books carry printed OIDs, so the production matcher (review_table.fuzzy_match_fields) starts from OIDs it already has — it fuzzy-matches form names (get_standard_crf, partial_ratio ≥ 70) and then reuses library rules whose OID sets the book covers. The name→OID mapper is the new component that reconstructs the missing link for unannotated books and feeds that same downstream. Reading the ladder: scoping to the matched form kills the cross-form errors — A’s worst failures were generic labels like “Collection Date” on the Central Laboratory form mapping to DMDAT, the Demographics date (17% → 76%). D0 isolates the scoping change from the ranker: its looser production-convention scope admits one more perfect-label impostor, and that is precisely the lesson — “Contact Method” scored 100 against a library row from the wrong follow-up form. The ranker (D0 → D) then vetoed that impostor and re-mapped all four abstained ties correctly (AGE not AGE_DV, AEACN not QVAL_AEACN<TRTCD>), which is why D judges even single candidates instead of auto-accepting them. String scores generate candidates; they never certify them.

D’s one remaining miss is unwinnable with this library: the book prints truth OID RACEOTH, but the 286-row extract only contains the variant QVAL_RACEOTH under the same label — the right answer isn’t on the shelf. Which is the general story of the maps column too: coverage falls from 8% to 1% under scoping because the extract rarely contains the form at all. The binding constraint on coverage is library breadth (production’s full ecs_index plus its stored field embeddings widen candidate generation; the funnel judges whatever candidates exist). On the other two books — no truth available — the funnel behaves identically: MAC186 mapped 12 of 857 pairs, QSC 15 of 1,271, every one ranker-judged, zero left ambiguous.

The asymmetry that decides the whole design: an unmapped field is not dropped — the production generator writes brand-new rules with the LLM from the form and field names alone, tagged source: "LLM Generated" for reviewer scrutiny (review_table.fuzzy_match_fields → make_llm_call_batch). That path is the workhorse, not the exception: on this very book the production output split was 697 LLM-generated rules vs 140 Standard + 73 Historical reused from the library. A mismapped OID, by contrast, silently attaches the wrong form’s library rules. So the funnel is built to prefer silence over guessing at every layer — the OID join exists to reuse curated rules where it can; it was never a gate on rule generation.

11Design choices, quickly

In one sentence: every choice optimizes for the same three things — bounded cost, determinism, and refusing to hardcode any format knowledge.

QuestionAnswer
Why doesn’t the pipeline “know” any CRF formats? Because the format space is unbounded. The only shipped knowledge is generic: PDFs have lines with geometry, layouts repeat within a document, and a parser can be validated by running it. Everything format-specific is discovered per document and thrown away after.
Why generated code instead of LLM answers? Code is auditable (read it), deterministic (same input → same output), free to re-run (404 pages, no tokens), and diffable across versions. Answers are none of those.
Why not a vision model on page images? The text layer already gives exact strings and coordinates for ~0 cost. Vision adds price and noise for born-digital PDFs. Scanned documents are flagged at stage 0 and would get an OCR front-door (e.g. Textract) that feeds the same Line interface.
What if one document needs two different parsers? That’s what the coverage-confirmation cycle is for: dark stacks go back to the model, which either proves they’re field-free or extends the program with another branch — the extension consumes loop budget like any other version.
What if the model just can’t crack a format? The loop stops on plateau or budget and the document is flagged needs_manual_template with its full trail attached. A wrong-but-confident output is never exported silently.
Does it depend on English? No. The layout tokens and the prompt contract are structural (geometry, boldness, character classes), not lexical; label “human-ness” checks accept non-Latin scripts.
What does a 1000-page document cost? The same as a 100-page one: LLM cost scales with the number of layout stacks (4–12 rep pages; 7–10 calls in the benchmark runs, hard-capped at ~16 with every audit reprompt counted), not the number of pages. Page count only adds cheap deterministic replay time.

12.1  From one parser to many passes — multi-pass specialists

feedback loop

Before: one codegen prompt carried ~4–12 representative pages and asked for a single parser for the whole book (§3–§4). Symptom: books with many distinct layout families (the 913‑page form tracker, the 1083‑page 331 books, the 35‑cluster 2021 book) have more families than fit one prompt’s rep budget, so the tail families never reach the model and stay dark.

Change: plan_passes (in codegen.py) can now split a document into a generalist pass 1 covering the budgeted clusters plus one or more tail specialist passes that own the leftover families. Each pass runs its own induction loop; the harness masks coverage to the pass’s assigned pages and merges the extractors.

The regression this caused — and the fix

The first cut gave every pass an ownership note (“you own ONLY the layout families shown…”). Sonnet took it literally and wrote narrow, representative‑matching parsers, collapsing the generalist pass:

bookgeneralist pass v1 (with note)identical model, no note
MAC186 (913p)5% coverage / 327 records88% / 4,852 records

Three books collapsed this way (MAC186 −85% fields, 04_Jul −65%, aCRF_16JAN −59%), dragging Sonnet page recall 76% → 63%. GPT largely ignored the framing and kept doc‑wide parsers, so it was not hurt — a sign the problem was prompt wording, not architecture.

Fix (two parts): (1) pass 1 is now a pure generalist whose initial/revision/confirm prompts are byte‑identical to a single‑pass run — no ownership language anywhere; only tail passes keep a note, reworded from behavior‑restricting to harness‑descriptive (“the harness credits you only for your pages and over‑extraction costs nothing, so write as if you owned the whole document”). (2) Splitting made rare: a tail pass is spawned only when it is substantial — ≥ 8 tail rep pages and ≥ 20 content pages — otherwise the tail folds back into pass 1.

Effect: split rate dropped 9/11 → 3/11 books; Sonnet page recall recovered to 75.5% at three fewer specialist passes per corpus run; 04_Jul’s generalist pass alone reached 88% coverage (vs 5% under the note). Full collapse trail and per‑book deltas: loop‑2 report §4 (symptom) and §8 (fix + validation).

12.2  A loop that explores — audit rotation, promotion, coverage confirm

feedback loop LLM call

Before: the grounded audit (§7) sampled a small fixed set of pages and re‑checked roughly the same ones each round. Change: audit samples grew (6 → 9–12 pages), the sampler now rotates to fresh pages every round instead of re‑auditing the same six, and pages the audit flags are promoted into the extractor’s coverage cores so the next revision must satisfy them (trails literally show “audit core grew by [5]”).

Sparse‑scope softening + CONFIRM_NO_FIELDS: a pass that produces zero records is no longer an automatic failure. On MAC186 a tail pass went 0 records → 116 records at 94% scope coverage through the confirm round; on aCRF_16JAN the model correctly answered “this 7‑page scope is furniture‑only” in just 2 calls. Under loop‑1 gates both would have been flagged needs_manual_template.

12.3  Protecting real coverage — evidence‑based junk carve‑out

deterministic

Before: when a new version dropped pages, improves() guessed whether the loss was “junk cleanup” from proxies (audit issues down on shared pages, few new pages, and a hard half‑retention floor). Symptom: that floor baked in an assumed junk‑to‑content ratio, and the inference had no idea what was on the dropped pages. On MAC186 it blessed a version that shed ~340 pages / ~3,000 real records to buy a 1‑issue audit improvement measured on a 13‑page sample.

Change (generic, evidence‑scaled, no ratio knobs): a lost page is forgiven only if every record the incumbent extracted on it matches verified junk evidence — values the page‑grounded audit explicitly flagged as false, or doc‑wide furniture candidates (a value present on ≥ 70% of pages). Matching is normalized exact‑value, because junk is a repeated stamp. The failure direction is one‑way: missing evidence keeps junk (a visible, bounded cost); it never releases real coverage (the invisible, unbounded MAC186 failure). Forgiven drops are recorded in the trail (forgiven_pages) so a coverage‑sacrificing best‑switch is diagnosable after the fact.

12.4  Getting form_name right — the four‑layer title fix

LLM call deterministic gate

Before: the contract said form_name is “the CRF form/section the field belongs to.” On annotated CRFs two printed signals compete: the page’s form title and each field’s annotation stamp. Symptom: on the same book, GPT loop‑1 produced 6 forms (correct titles), Sonnet 7 — but loop‑2 GPT produced 331 distinct forms out of 996 records, using per‑field stamps like "Exclusion: E05 #1" as the form name. Form accuracy 18/51 (Sonnet: near‑perfect on the same pages). Four structural layers were added, none fitted to this corpus’s annotation shapes:

1 · Contract by definition

The prompt now defines form_name as the title printed for humans that groups a form’s fields and is carried across continuation pages — never text attached to a single field. States the self‑check: near‑unique form per record means per‑field text was read.

2 · Two‑tier structural gate

gate_form_explosion: ≥ 20 records averaging < 2 fields/form violates the grouping definition — hard gate. Average < 4 is an advice warning. Scoped specialist passes are not exempt.

3 · Audit given the convention

The wrong_form audit channel now explicitly covers form_name values that are not printed titles, so page‑grounded findings block convergence in the 2–4 fields/form band the hard gate deliberately leaves open.

4 · Independent title‑context channel

Stage 0 finds top‑region strings that change by a run of pages (not chrome present on ≥95% of pages), dumps up to six as title_p* in a TITLE/FORM CONTEXT ONLY prompt block, and gives each audited page the top region of its two preceding pages as lookback. No layout ownership, no coverage effect.

Effect: on the 112‑page 326 book, GPT form accuracy went 0/10 → 10/10 with the title channel while Sonnet stayed 10/10; corpus GPT forms climbed 18 → 28 → 44/57 across the layers. Caveat: the signal is necessary but not sufficient — on the 489‑page 326 book GPT still scored 0/10 because a repeated non‑title annotation satisfies same‑page persistence, which is why a Sonnet‑generate / GPT‑audit hybrid exists as a targeted fallback (recovered that book to 10/10). Layer‑by‑layer implementation and evidence: loop‑2 report §7 (contract + gate), §11 (title channel); hybrid results in the backpocket report §5.

12.5  Not overfitting to the samples shown

LLM call AST guard

A recurring failure mode: the model writes a parser that pattern‑matches the exact strings on the few pages it was shown, instead of the general structure. Three defenses:

  • Family‑labeled prompts. Rep pages are grouped and labeled by structural layout family; the generator is asked for a handler‑per‑family plus a structural dispatcher, tolerant/relative geometry, and no literal‑text blocklists. This recovered MAC186 Sonnet page recall 44.6% → 62.4% (859/913 pages) — but regressed GPT on the 326 book to 0 TP. So it was made optional and model‑neutral: family labels stay (they help Sonnet), the architecture is not forced on simple single‑family layouts.
  • Literal‑blocklist AST detection. A static check counts literal text filters in the generated program (including named collections/sets). Prompt advice alone did not stop the behavior (MAC186 grew 11 → 15 → 18 filters despite guidance), so it became a real gate: warn at 10, hard‑reject at 30. In the final run this rejected multiple 30–71‑filter versions while keeping earlier, less content‑fitted ones eligible.
  • Diversity / radius‑driven representatives. Reps are chosen for structural spread within a cluster, and coverage confirmation dumps holes first, so the model sees varied in‑family samples rather than near‑duplicates.

12.6  Scaling & reliability plumbing

deterministic
  • Size‑scaled version budget: +1 parser version at 900 pages, capped at +2 — more revisions for genuinely large books. (Effect is mixed: GPT gained +10.7pp page recall on both 331 books; Sonnet gained on one and lost on the other. Marginal v6 value should be confirmed from trails before keeping it universally.)
  • Stale‑artifact purge per tag before a run, collision‑resistant composite tags for hybrid model runs, and per‑(config, model) isolated output directories so concurrent runs never overwrite each other’s prompts/replies.
  • Per‑pass profiling and a mechanical multi‑pass orchestration test (stale purge, worst‑status merge, per‑pass profile slicing). Result: 22/22 document runs exported across both models with no crashes or transport failures.

12.8  Cluster‑sampling ablation → approach D (current best for Sonnet)

experiment

A four‑way ablation tested how to divide work between the generalist pass and the offloaded specialist passes, driven entirely by env‑gated knobs (no format knowledge): a = baseline, b = more samples for one fat generalist, c = narrow split (many small agents, one sample each), d = few clusters per agent and more samples per cluster, offloaded. Expressing d required a new knob, ECS_SPECIALIST_REPS_PER_CLUSTER (default 1 = unchanged): until now every offloaded cluster was hardwired to a single sample page, so “more samples per cluster” never reached the specialists.
