CRF digitizer · supporting any unknown CRF format

To digitize a CRF it has never seen, the AI writes a parser for that exact document,
then proves it works — testing, reviewing and fixing its own code in a loop.

Hardcoded templates can’t cover every study’s format, and having AI read 1,000 pages is slow and unrepeatable. So the AI reads a handful of sample pages (6 here), writes a small parser for this document, and plain Python runs it over every page. Everything below is one real run: a 404-page Rave CRF, 7 AI calls total.
The real run · 7 AI calls ① writes parser v1 → 954 records, but the dominant layout group (249 pages) came back empty  →  ② shown those pages: “data dictionaries, not entry forms” → correctly field-free  →  ③ page audit: 8 issues, e.g. p4 instruction extracted as a field, p91 four “ECG Recording” fields missed  →  ④ rewrites its code → v2, 1,242 records  →  ⑤ re-audit, same pages: 8 → 4 issues, new best  →  ⑥ v3 audits cleaner but drops 22% of covered pages → guard refuses → stop, best (v2) exported
Same loop, zero configuration, on three formats it had never seen: Rave CRF 404p → 1,242 fields / 76 forms  ·  QSC eSource 609p → 1,823 / 16  ·  MAC186 tracker 913p → 6,165 / 73  —  7–10 AI calls each, whatever the page count.
